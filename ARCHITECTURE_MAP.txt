HOW TO READ THIS DOCUMENT
-------------------------
Every file carries a one-line note plus a status tag:

  LIVE     Reads or writes the real Supabase database at request time.
  HYBRID   Real data at build time (bundled JSON), demo data at runtime.
  STUB     Hardcoded in the file, localStorage, or UI-only. No database.
  INPUT    Data consumed by a script, never imported by the app.
  CONFIG   Environment, build or tooling configuration.

"Bundled JSON" is important: src/lib/curriculum/index.ts imports the five
package JSON files with static `import` statements. Next.js compiles them into
the server bundle. The app therefore renders curriculum from disk at build
time, not from Supabase at run time.

2.1 SHAPE OF THE APP
--------------------
        Browser
           |
           v
  Next.js 15 App Router (server components by default)
           |
     +-----+---------------------+----------------------+
     |                           |                      |
  Bundled JSON            Server actions          Route handlers
  (curriculum packages)   (parent area)           (/api/*)
     |                           |                      |
     |                           v                      v
     |                    Supabase (service role, no RLS enforcement)
     |                           |

Two data paths never meet:
  - Curriculum is compiled into the bundle from curriculum-packages/*.json.
  - Learner state is either the demo record in data/workspace.ts or a direct
    service-role call from a server action / route handler.

Nothing in the app reads the curriculum tables from Postgres. Importing a
package into Supabase updates the database but changes nothing on screen until
the app switches from bundled JSON to a repository read.

2.3 AUTHENTICATION AND THE GUARDIAN PIN
---------------------------------------
There is no Supabase Auth session in use. No sign-in, no JWT, no auth.users row.
The app is a single-household installation guarded by a numeric PIN.

  Onboarding (first run)
    /parent/onboarding -> OnboardingWizard (client)
      -> completeOnboardingAction (server action)
         1. zod-validate FormData
         2. INSERT households (guardian_pin_hash = scrypt:<salt>:<hash>)
         3. INSERT profiles  x2  (parent_educator, student)
         4. INSERT academic_terms x3
         5. INSERT learner_term_enrollments per subject/term
         6. cookies().set("openigcse_parent", "1", httpOnly, sameSite lax, 8h)
         7. redirect("/parent")

  Guardians gate (every visit after that)
    (parent)/parent/(gated)/layout.tsx
      cookie openigcse_parent == "1" ?
        yes -> render children
        no  -> <ParentGate/> -> unlockParent(pin)
                 pinMatches(pin)  -> read households.guardian_pin_hash, scrypt import
                 on success       -> set the same cookie, redirect /parent
    Bypass: when ONBOARDING_BYPASS=true AND no household exists, the gate is skipped
    so the demo can be browsed. That combination is deliberate.

  Weak points, stated plainly
    - The cookie value is the literal string "1". It is httpOnly and set only by
      the server, but it is not signed and not tied to a session table. Anyone
      who can write cookies on the device can bypass the gate.
    - PIN comparison uses timingSafeEqual on scrypt output (good), but there is
      no attempt counter, no lockout, and no audit of failed unlocks.
    - setGuardianPin() targets the earliest household row by created_at.
    - The service-role key sits in .env.local on the server only. No client
      bundle contains it, but a single Next.js process holds full database
      authority for every request.

2.4 THE DATA SEAM (src/lib/data/)
---------------------------------
  data/session.ts     REAL. Reads profiles+households through the admin client.
                      Used by the student layout, the parent gate and onboarding.
  data/workspace.ts   DEMO. Returns Workspace with source:"demo". Every export of
                      this file is built from literal arrays plus a hash() of the
                      objective code to fake mastery.
  data/trivia.ts      DEMO. Three literal modules.

  How the seam "decides": it does not. getWorkspace() never queries Supabase and
  has no fallback branch - it is the fallback. Only getSetupState() touches the
  database, and pages do not combine the two. A configured household changes the
  redirect behaviour and the learner name in the sidebar; it does not change any
  page content.

  Every place demo or hardcoded state still exists:
    1. data/workspace.ts  - learner, term (always "Term 2" spanning today +/-),
                            assessments x3, mistakes x4, checkpoints x3,
                            resources x3, events x4, mastery hash, hasLesson flag.
    2. data/trivia.ts     - three modules and their checkpoints.
    3. TermPlanner        - localStorage "openigcse.term-plan".
    4. MarkingDesk        - localStorage marks/tags/logged; checkpoints come from
                            data/workspace.ts.
    5. FocusControls      - localStorage "openigcse.focus".
    6. StudyBlock         - reorder state in React state only; "done" list in state.
    7. progress pages     - mastery percentages derived from the synthetic signals.
    8. parent overview    - "3 open", "No open help requests", package counts.
    9. config/site.ts     - region/zone/stage lists (appropriate to keep static).

--------------------------------------------------
  Phase 1 - make the seam real (highest leverage, nothing else works without it)
    1. Add repository functions in src/lib/data/ for one entity at a time, starting
       with the learner's term: readTerm(householdId), termEnrollments(studentId).
    2. Change getSetupState to also return learnerId + activeTermId, and pass them to
       getWorkspace(). Delete the demo branches page by page, not all at once.
    3. Replace getWorkspace() with an async getLearnerWorkspace() that reads
       academic_terms, learner_term_enrollments, learning_events, mistake_notebook,
       term_assessments. Keep the demo version behind
       `if (process.env.DEMO_MODE === "true")` for screenshots only.
    4. Switch curriculum reads from bundled JSON to topics/learning_objectives once
       extraction works (they already hold identical shapes).

  Phase 2 - make the parent side write
    5. Term planner server action: upsert academic_terms by (household_id, name) and
       learner_term_enrollments by (student_id, academic_term_id, entry_route_id).
    6. Question bank editor: create/update question_templates against a
       learning_objective_id.
    7. Assessment builder: term_assessments + assessment_items, then a marking screen
       that writes assessment_item_marks and, on any deducted mark, inserts
       mistake_notebook with the chosen error_category. Return real UUIDs so
       /review Resolve works.
    8. Focus settings: replace localStorage with a focus_sessions table or columns on

    9. Write checkpoint outcomes as learning_events (Formal_Assessment) with score_ratio,

   10. Feed the NBA engine from real rows: open mistakes per objective, days since last
       learning_event, and days to the next term_assessment.
   11. Persist study-block ordering per day (a small day_plan table or a jsonb column).

   12. Rewrite parseSubjectContent for the real layouts: heading variants
